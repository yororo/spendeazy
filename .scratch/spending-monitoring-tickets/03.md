## What to build

Users filtering Transactions see the complete filtered count and expense total, with clearly secondary whole-month context.

Scope: parent User Stories 37; ID-3, ID-4.

## Acceptance criteria

- [ ] Show the total count and expense amount for the complete filtered result across pagination, not the current page or an unfiltered month.
- [ ] Any whole-month count or amount is explicitly labeled and secondary; filters and summaries visibly agree.
- [ ] Category, date, search, and account filters update both result and summary; clearing filters restores normal monthly results.
- [ ] Reset pagination and isolate cache identity when filter or Space scope changes; avoid showing a stale summary under a new filter.
- [ ] Use existing query/API boundaries; inspect available summary capabilities and paginate/aggregate correctly if needed, rather than assuming the first page is the complete result. Any contract adjustment is validated on API and browser sides.
- [ ] Verify multiple pages, combined filters, empty results, failure/retry, and preservation of Reporting Period and Space.

## Blocked by

None — can start immediately.

## Implementation and validation guardrails

Use existing feature/page/service and isolated browser → API → PostgreSQL test seams. Each slice owns its meaningful regression tests and runs required owning-project checks plus the repository-required isolated end-to-end suite before completion. Preserve accepted Rule-storage/reconciliation ADRs, frontend feature boundaries, existing authorization and atomic import behavior; validate both sides of any discovered API contract adjustment. No new test framework, Review editing, numerical forecasts, automatic Budget changes, or private financial fixtures.
