## What to build

Users immediately see selected-month risks and can investigate Transactions or edit/set a Category Budget while preserving context.

Scope: parent User Stories 38–41; ID-3.

## Acceptance criteria

- [ ] Place the selected Reporting Period, recorded spending summary, and Category attention states before historical totals/charts.
- [ ] Surface individual Nearing Budget, At Budget Limit, and Over Budget states; do not present a breach in a low-spending ranking without its warning.
- [ ] Provide View Transactions and Edit Budget/Set Budget actions carrying Space, month, and Category; return/cancel restores the originating view and filters.
- [ ] Budgeted, total, and Unbudgeted summaries use the agreed scope and exact status policy; no-budget and empty states provide useful actions without completeness claims.
- [ ] For the current month, show actual usage alongside elapsed-month progress labeled as recorded spending. Historical periods show actual historical spending; do not add numerical forecasts.
- [ ] Verify contextual handoffs, filtered totals, return/cancel, changed Reporting Period, mobile hierarchy, desktop consistency, and accessibility. Statement-scoped browsing is not a prerequisite for month-scoped actions.

## Implementation and validation guardrails

Use existing feature/page/service and isolated browser → API → PostgreSQL test seams. Each slice owns its meaningful regression tests and runs required owning-project checks plus the repository-required isolated end-to-end suite before completion. Preserve accepted Rule-storage/reconciliation ADRs, frontend feature boundaries, existing authorization and atomic import behavior; validate both sides of any discovered API contract adjustment. No new test framework, Review editing, numerical forecasts, automatic Budget changes, or private financial fixtures.
