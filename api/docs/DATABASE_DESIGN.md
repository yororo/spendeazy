# Expense Tracker Relational Database Schema

## Purpose

This document defines the recommended relational database schema for a simple personal expense-tracking application.

The application supports:

- Users
- User-defined expense categories
- Monthly or yearly category budgets
- Manually entered expense transactions
- Transactions imported from credit-card statement PDFs
- Provenance tracking for successfully imported statements
- Automatic category assignment during import using category rules
- Duplicate statement detection
- Probable duplicate transaction detection
- Future multi-user support

The application currently supports **expenses only** and **one currency only**.

The schema should remain intentionally simple. Do not introduce financial account, bank, card, household, income, transfer, or accounting-ledger entities unless requirements change.

---

# General Conventions

## Naming

Use `snake_case` for database identifiers.

Examples:

- `user_id`
- `category_id`
- `statement_import_id`
- `created_at`

Foreign-key columns must use the referenced entity name followed by `_id`.

Prefer explicit domain names such as `purchase_date` instead of generic names such as `date`.

---

## Primary Keys

Recommended logical type:

```text
BIGINT
```

Primary-key values should be generated by the database using an auto-incrementing identity column.
Prefer the standard `GENERATED ALWAYS AS IDENTITY` behavior where supported, or the closest
database equivalent.

Foreign-key columns must use `BIGINT` so they match the referenced primary key.

---

## Timestamps

Store timestamps in UTC.

Recommended logical type:

```text
TIMESTAMP WITH TIME ZONE
```

or the closest database equivalent.

Timestamps should contain at least millisecond precision when supported.

Common fields:

```text
created_at
updated_at
imported_at
```

`created_at` must be populated when the row is created.

`updated_at` must initially equal `created_at` and be updated whenever the row changes.

`imported_at` represents when a successfully reviewed statement import was committed to the database.

Do not use local application time as the stored timestamp.

---

## Monetary Values

Never use floating-point types such as:

```text
FLOAT
REAL
DOUBLE
```

for monetary values.

Use:

```text
DECIMAL(15,2)
```

or:

```text
NUMERIC(15,2)
```

All current transaction and budget amounts are positive.

Example:

```text
250.00
42.42
12.99
```

Negative values are not currently supported because the application models expenses only.

---

## Currency

The application currently supports one currency only.

Do **not** add a currency column unless multi-currency support becomes a requirement.

Currency formatting belongs to the application/configuration layer.

---

# Entity Relationship Overview

```text
users
 ├── categories
 │    ├── budgets
 │    ├── category_rules
 │    └── transactions
 │
 ├── transactions
 │
 └── statement_imports
      └── transactions
```

Cardinalities:

```text
users             1 ─── * categories
users             1 ─── * transactions
users             1 ─── * statement_imports
users             1 ─── * category_rules

categories        1 ─── * transactions
categories        1 ─── 0..1 budgets
categories        1 ─── * category_rules

statement_imports 1 ─── * transactions
```

# Table: `users`

Represents an application user.

## Columns

| Column       | Type           | Nullable | Notes        |
| ------------ | -------------- | -------: | ------------ |
| `id`         | BIGINT         |       No | Auto-incremented primary key |
| `name`       | `VARCHAR(200)` |       No | Display name |
| `email`      | `VARCHAR(320)` |       No | User email   |
| `created_at` | timestamp      |       No | UTC          |
| `updated_at` | timestamp      |       No | UTC          |

## Constraints

```text
PRIMARY KEY (id)
UNIQUE (email)
```

Email uniqueness should ideally be case-insensitive.

The implementation method may depend on the selected database.

Examples include:

- normalized lowercase email
- case-insensitive collation
- PostgreSQL `citext`

The application should normalize email before persistence.

Recommended normalization:

```text
trim
lowercase
```

---

# Table: `categories`

Represents a user-defined expense category.

Examples:

```text
Groceries
Transport
Dining Out
Utilities
```

Categories are owned by users and may be renamed.

## Columns

| Column        | Type           | Nullable | Notes                         |
| ------------- | -------------- | -------: | ----------------------------- |
| `id`          | BIGINT         |       No | Auto-incremented primary key |
| `user_id`     | BIGINT         |       No | Owner                         |
| `name`        | `VARCHAR(100)` |       No | User-visible category name    |
| `description` | `VARCHAR(500)` |      Yes | Optional category description |
| `color`       | `VARCHAR(32)`  |      Yes | Saved named palette identifier; null for a legacy/unselected Category |
| `is_active`   | BOOLEAN        |       No | Default `TRUE`                |
| `created_at`  | timestamp      |       No | UTC                           |
| `updated_at`  | timestamp      |       No | UTC                           |

## Constraints

```text
PRIMARY KEY (id)

FOREIGN KEY (user_id)
    REFERENCES users(id)

UNIQUE (user_id, name)

UNIQUE (id, user_id)

CHECK (color IS NULL OR color IN (the 24 supported named Category Color identifiers))
```

The `(id, user_id)` unique constraint exists to support composite foreign keys from user-owned tables and prevent cross-user references.

Category Color is Category-owned data. The API accepts and stores one of the 24 named palette identifiers (never a hex value); null remains valid for existing records. A null stored value is presented using a deterministic default derived only from the Category ID, so it stays stable across renames, list order, periods, and reloads. An explicitly saved color takes precedence and is retained when the Category is renamed, deactivated, or reactivated.

### Category name uniqueness

Category names must be unique per user.

Valid:

```text
John → Groceries
Jane → Groceries
```

Invalid:

```text
John → Groceries
John → Groceries
```

Category-name comparison should preferably be case-insensitive.

These should normally be considered duplicates:

```text
Groceries
groceries
GROCERIES
```

Normalize category names or use an appropriate database collation/index strategy.

---

## Category deletion behavior

Prefer **logical deactivation** instead of physical deletion.

When a user "deletes" a category from the UI:

```text
is_active = FALSE
```

The category should no longer appear as an option for new transactions but historical transactions should retain their category relationship.

This preserves historical reporting.

If physical category deletion is implemented anyway:

```text
transactions.category_id → ON DELETE SET NULL
budgets.category_id      → ON DELETE CASCADE
category_rules.category_id → ON DELETE CASCADE
```

Logical deactivation is preferred.

---

# Table: `budgets`

Represents the recurring spending limit for a category.

A user may define **at most one budget per category**.

Examples:

```text
Groceries → 10000 monthly
Travel    → 120000 yearly
```

A category cannot simultaneously have both a monthly and yearly budget.

## Columns

| Column        | Type            | Nullable | Notes                 |
| ------------- | --------------- | -------: | --------------------- |
| `id`          | BIGINT          |       No | Auto-incremented primary key |
| `category_id` | BIGINT          |       No | Budgeted category     |
| `period`      | `VARCHAR(20)`   |       No | `monthly` or `yearly` |
| `amount`      | `DECIMAL(15,2)` |       No | Positive              |
| `created_at`  | timestamp       |       No | UTC                   |
| `updated_at`  | timestamp       |       No | UTC                   |

## Constraints

```text
PRIMARY KEY (id)

FOREIGN KEY (category_id)
    REFERENCES categories(id)
    ON DELETE CASCADE

UNIQUE (category_id)

CHECK (period IN ('monthly', 'yearly'))

CHECK (amount > 0)
```

### Why `user_id` is not stored

Budget ownership can be derived through:

```text
budget
  → category
    → user
```

Therefore `budgets.user_id` would duplicate ownership data unnecessarily.

---

# Table: `statement_imports`

Represents one successfully reviewed and committed credit-card statement import.

One row corresponds to exactly one imported statement file.

A `statement_imports` row must only be created when the user has completed review and confirmed the import.

Do not persist temporary parsing/review state here.

## Columns

| Column           | Type           | Nullable | Notes                                 |
| ---------------- | -------------- | -------: | ------------------------------------- |
| `id`             | BIGINT         |       No | Auto-incremented primary key          |
| `user_id`        | BIGINT         |       No | Owner                                 |
| `file_name`      | `VARCHAR(255)` |       No | Original uploaded file name           |
| `file_hash`      | `CHAR(64)`     |       No | SHA-256 hex digest of uploaded file   |
| `statement_date` | DATE           |       No | Statement date parsed from document   |
| `bank`           | `VARCHAR(100)` |       No | Bank name/code parsed from statement  |
| `card_type`      | `VARCHAR(100)` |      Yes | Example: `amex`, `visa`, `mastercard` |
| `imported_at`    | timestamp      |       No | Successful commit time in UTC         |

## Constraints

```text
PRIMARY KEY (id)

FOREIGN KEY (user_id)
    REFERENCES users(id)

UNIQUE (user_id, file_hash)

UNIQUE (id, user_id)
```

Optionally add a logical-statement uniqueness constraint if applicable:

```text
UNIQUE (user_id, bank, card_type, statement_date)
```

This constraint should only be enabled if the product treats that combination as uniquely identifying one statement.

---

## `file_hash`

`file_hash` should contain the SHA-256 hash of the **original uploaded PDF bytes**.

Expected format:

```text
64-character lowercase hexadecimal string
```

Example:

```text
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
```

Purpose:

```text
detect exact duplicate file imports
```

Filename must **not** be used for duplicate detection.

---

## Statement import transaction boundary

Statement import creation and transaction insertion must occur inside a single database transaction.

Conceptually:

```text
BEGIN

INSERT statement_import

INSERT transaction 1
INSERT transaction 2
...
INSERT transaction N

COMMIT
```

If any insert fails:

```text
ROLLBACK
```

The database should never contain a successful `statement_imports` record with only a partially imported transaction set.

---

# Table: `transactions`

Represents one expense transaction.

Transactions may be:

```text
manual
imported
```

No explicit `type` or `source` column is required.

The source is inferred from `statement_import_id`.

```text
statement_import_id IS NULL
    → manually entered

statement_import_id IS NOT NULL
    → imported from statement
```

## Columns

| Column                      | Type            | Nullable | Notes                                       |
| --------------------------- | --------------- | -------: | ------------------------------------------- |
| `id`                        | BIGINT          |       No | Auto-incremented primary key                 |
| `user_id`                   | BIGINT          |       No | Transaction owner                           |
| `category_id`               | BIGINT          |      Yes | Expense category                            |
| `statement_import_id`       | BIGINT          |      Yes | Source import, null for manual transactions |
| `purchase_date`             | DATE            |       No | Purchase date only                          |
| `description`               | `VARCHAR(500)`  |       No | Merchant/statement/user description         |
| `amount`                    | `DECIMAL(15,2)` |       No | Positive expense amount                     |
| `category_match_confidence` | `DECIMAL(5,4)`  |      Yes | Imported category confidence, range 0..1    |
| `import_fingerprint`        | `CHAR(64)`      |      Yes | Probable duplicate detection signal         |
| `created_at`                | timestamp       |       No | UTC                                         |
| `updated_at`                | timestamp       |       No | UTC                                         |

## Constraints

```text
PRIMARY KEY (id)

FOREIGN KEY (user_id)
    REFERENCES users(id)

FOREIGN KEY (category_id, user_id)
    REFERENCES categories(id, user_id)

FOREIGN KEY (statement_import_id, user_id)
    REFERENCES statement_imports(id, user_id)

CHECK (amount > 0)

CHECK (
    category_match_confidence IS NULL
    OR (
        category_match_confidence >= 0
        AND category_match_confidence <= 1
    )
)
```

If every imported transaction always has a category confidence value, optionally enforce:

```text
CHECK (
    (
        statement_import_id IS NULL
        AND category_match_confidence IS NULL
    )
    OR
    (
        statement_import_id IS NOT NULL
        AND category_match_confidence IS NOT NULL
        AND category_match_confidence >= 0
        AND category_match_confidence <= 1
    )
)
```

Use this stronger constraint only if the import pipeline guarantees confidence values.

---

## `category_id`

May be null.

Examples:

```text
categorized transaction:
category_id = Groceries

uncategorized transaction:
category_id = NULL
```

If categories are deactivated instead of physically deleted, old transactions should retain their category IDs.

---

## `statement_import_id`

Nullable provenance relationship.

Expected values:

```text
NULL
```

for manually entered transactions.

Example imported transaction:

```text
statement_import_id = 42
```

One imported transaction belongs to exactly one statement import.

Do not create a transaction/import junction table unless future requirements allow one transaction to originate from multiple statement imports.

---

## `category_match_confidence`

Only populated for imported transactions when automatic categorization occurs.

Range:

```text
0.0000 .. 1.0000
```

Examples:

```text
1.0000 = deterministic/exact match
0.8500 = high-confidence match
0.5000 = uncertain match
NULL   = no automatic category confidence
```

Manual transactions should normally have:

```text
NULL
```

The database does not need to retain original suggested categories after user review.

---

## `import_fingerprint`

Used as a **probable duplicate signal**, not guaranteed transaction identity.

Recommended input fields:

```text
purchase_date
normalized_description
amount
bank
card_type
```

Conceptual input:

```text
2026-08-01|STARBUCKS|150.00|BDO|AMEX|1234
```

Hash this normalized value using SHA-256.

Expected persisted value:

```text
64-character hexadecimal string
```

Do **not** add a global unique constraint on `import_fingerprint`.

Two legitimate transactions may have identical:

```text
date
merchant
amount
card
```

Example:

```text
2026-08-01 Starbucks 150.00
2026-08-01 Starbucks 150.00
```

A fingerprint collision should trigger duplicate review logic, not automatic rejection.

---

# Table: `category_rules`

Represents a user-defined rule for automatically assigning a category during statement import.

Frontend review behavior:

```text
transaction description matched against a rule pattern
    → assign category
```

The API stores `exact` and `contains` rules. The frontend evaluates these rules during statement review; the API does not perform description matching or choose precedence.

## Columns

| Column               | Type           | Nullable | Notes                              |
| -------------------- | -------------- | -------: | ---------------------------------- |
| `id`                 | BIGINT         |       No | Auto-incremented primary key       |
| `user_id`            | BIGINT         |       No | Rule owner                         |
| `category_id`        | BIGINT         |       No | Category assigned on match         |
| `pattern`            | `VARCHAR(500)` |       No | Original user-visible rule pattern |
| `normalized_pattern` | `VARCHAR(500)` |       No | Normalized matching value          |
| `match_type`         | `VARCHAR(30)`  |       No | `exact` or `contains`               |
| `created_at`         | timestamp      |       No | UTC                                |
| `updated_at`         | timestamp      |       No | UTC                                |

## Constraints

```text
PRIMARY KEY (id)

FOREIGN KEY (user_id)
    REFERENCES users(id)

FOREIGN KEY (category_id, user_id)
    REFERENCES categories(id, user_id)
    ON DELETE CASCADE

CHECK (match_type IN ('exact', 'contains'))

UNIQUE (
    user_id,
    match_type,
    normalized_pattern
)
```

---

## `pattern`

Stores the rule as entered/displayed to the user.

Example:

```text
Green Market
```

---

## `normalized_pattern`

Stores the canonical comparison value.

Recommended normalization:

```text
1. trim leading/trailing whitespace
2. lowercase
3. collapse repeated whitespace
```

Example:

```text
"  Green   Market "
```

becomes:

```text
green market
```

This field is used for matching and uniqueness.

Do not rely solely on database collation rules for matching behavior because behavior differs across relational databases.

---

## `match_type`

Valid values:

```text
exact
contains
```

Individual creation defaults an omitted type to `exact`; an omitted update preserves the current type. Category replacement requires a type on each item. Remember is a frontend operation that creates Exact Rules through individual creation.

Uniqueness is per User, normalized pattern, and match type across all Categories, including inactive ones. Matching precedence belongs to the frontend.

No `priority` field is currently necessary.

---

# Cross-User Integrity

The database must prevent records owned by one user from referencing entities owned by another.

Invalid example:

```text
transaction.user_id = John
transaction.category_id = Jane's category
```

A normal FK on `category_id` alone would not prevent this.

Therefore user-owned tables should use composite integrity where practical.

Required category relationship:

```text
categories:
UNIQUE (id, user_id)

transactions:
FOREIGN KEY (category_id, user_id)
    REFERENCES categories(id, user_id)

category_rules:
FOREIGN KEY (category_id, user_id)
    REFERENCES categories(id, user_id)
```

Required import relationship:

```text
statement_imports:
UNIQUE (id, user_id)

transactions:
FOREIGN KEY (statement_import_id, user_id)
    REFERENCES statement_imports(id, user_id)
```

This makes cross-user references impossible even if application logic contains a bug.

# Recommended Indexes

Primary-key and unique constraints usually create indexes automatically.

Verify database behavior before creating redundant indexes.

## `users`

```text
UNIQUE INDEX users_email
    ON users(email)
```

Use normalized/case-insensitive email semantics.

---

## `categories`

```text
UNIQUE INDEX categories_user_name
    ON categories(user_id, name)
```

If logical deactivation is used, common category retrieval may benefit from:

```text
INDEX categories_user_active
    ON categories(user_id, is_active)
```

---

## `transactions`

Most common query pattern:

```text
transactions for user
filtered by date range
sorted by purchase date
```

Create:

```text
INDEX transactions_user_purchase_date
    ON transactions(user_id, purchase_date)
```

For category analytics:

```text
INDEX transactions_user_category_purchase_date
    ON transactions(user_id, category_id, purchase_date)
```

For retrieving imported transactions:

```text
INDEX transactions_statement_import
    ON transactions(statement_import_id)
```

For probable duplicate lookup:

```text
INDEX transactions_user_import_fingerprint
    ON transactions(user_id, import_fingerprint)
```

Do not make this index unique.

---

## `statement_imports`

For import history:

```text
INDEX statement_imports_user_statement_date
    ON statement_imports(user_id, statement_date)
```

`UNIQUE(user_id, file_hash)` should already provide an index for exact duplicate lookup.

---

## `category_rules`

The uniqueness constraint:

```text
UNIQUE(user_id, match_type, normalized_pattern)
```

should normally provide the primary matching index needed for exact rules.

---

# Recommended Delete Behavior

| Parent              | Child            | Behavior                                                                                   |
| ------------------- | ---------------- | ------------------------------------------------------------------------------------------ |
| `users`             | user-owned data  | Application decision; preferably restrict or transactional cascade during account deletion |
| `categories`        | `transactions`   | Prefer no physical deletion; otherwise `SET NULL`                                          |
| `categories`        | `budgets`        | `CASCADE`                                                                                  |
| `categories`        | `category_rules` | `CASCADE`                                                                                  |
| `statement_imports` | `transactions`   | Prefer `RESTRICT`                                                                          |

`statement_imports` should generally not be deleted independently while imported transactions remain because the import provides provenance.

If the application supports deleting an import and its transactions together, perform that operation explicitly inside one database transaction rather than relying blindly on cascading deletion.

# Transaction Creation Rules

## Manual transaction

Expected values:

```text
user_id                  = required
category_id              = optional
statement_import_id      = NULL
purchase_date            = required
description              = required
amount                   = positive
category_match_confidence = NULL
import_fingerprint       = NULL
```

Example:

```text
purchase_date = 2026-08-01
description = Monthly rent
amount = 250.00
category_id = Housing
statement_import_id = NULL
```

---

## Imported transaction

Expected values:

```text
user_id                  = required
category_id              = optional
statement_import_id      = required
purchase_date            = required
description              = required
amount                   = positive
category_match_confidence = 0..1 or NULL depending on categorization
import_fingerprint       = recommended
```

Imported transaction ownership must match the owning user of the referenced statement import.

# Implementation Principle

Prefer database-enforced invariants whenever they are cheap and portable.

Use:

```text
PRIMARY KEY
FOREIGN KEY
UNIQUE
CHECK
NOT NULL
```

to prevent invalid domain states.

Application validation improves user experience.

Database constraints protect data integrity.

Both should exist.

Avoid adding tables merely because values repeat. Introduce new entities only when they represent independent domain concepts with their own identity, lifecycle, relationships, or behavior.
