# Store Category Rules with Space-scoped atomic replacement

This decision records the current Space-scoped Rule storage invariants. Its former Personal route aliases are superseded and removed. The accepted [mobile Expense contract](../../../docs/specifications/mobile-expense-domain-api.md) assigns matching to the on-device mobile workflow.

The accepted [mobile Expense target decision](../../../docs/adr/0004-mobile-expense-domain-and-contract.md) extends this boundary to atomic Category/Budget/Rules configuration and atomic import-time remembered Rules, with full inactive configuration maintenance. It retains Space locking, normalized uniqueness and stable Rule identities. Those broader configuration/confirmation changes remain pending; this ADR's separate endpoints and active-only replacement are historical API behavior, not the target contract.

This decision supersedes the earlier per-User serialization scope and last-write-wins behavior. Category Rules belong to a Space, and every explicit Space route authorizes the authenticated User's membership before reading or mutating that Space. Legacy personal routes remain compatibility shims that resolve the authenticated User's Personal Space.

The API stores Exact and Contains Category Rules; the mobile client owns on-device rule evaluation, overlap precedence, and Remember (which creates Exact Rules). Statement Import continues accepting reviewed Category assignments. This keeps categorization policy with the review workflow rather than introducing a second matching implementation in the API.

Category replacement is atomic and Space-serialized. The Space stores a monotonic Category Rule revision; a replacement supplies the revision from its last read and is rejected as stale when another member has changed any Rule first. Individual scoped edits may also supply the returned `updatedAt` timestamp and are rejected when stale. Rules retain identity by normalized pattern and match type, preserving IDs and creation timestamps for retained rules and update timestamps for unchanged display patterns. Recreating every row would make retries unnecessarily change public identities. All scoped rule mutations lock the Space so replacement, individual mutations, and cross-Category uniqueness checks observe one consistent rule set.

Replacement requires an active Category in the destination Space even when clearing its rules. Existing individual maintenance of rules on inactive Categories remains allowed; creation and reassignment require an active Category in the destination Space. Duplicate conflicts apply only within the destination Space and identify the conflicting Category and request field, including duplicates within a replacement request. Exact and Contains matching semantics, on-device categorization, and the rule-update guarantee that reviewed assignments are not rewritten remain unchanged.
