# IP-04 Task 03 handoff

- Production parsing is independent of the legacy proof transformers and their throwing reconciliation semantics. BDO per-card subtotals/final total and card/wallet summary equations are checked over original signed activity, including excluded payments/credits. Wallet closing balance uses opening minus outgoing plus incoming; card balances use opening plus outgoing minus incoming.
- GCash's stream layout can omit the empty debit or credit column. In that case direction is accepted only when the adjacent balance difference exactly equals the row magnitude. The starting balance anchors the first row; missing pages break that chain. Explicit debit/credit values require the recognized table header. Descriptions never supply direction, and an unresolved row never changes sign to satisfy controls. Other variants need sanitized independent examples before support claims.
- Results retain normalized original posting-date text and wallet running-balance text in addition to the Task 01 model. Controls now retain source labels, components and BDO subtotals. Review must not replace these with edited totals or apply its inclusion choices to reconciliation.
- Date-only parsing uses calendar arithmetic without `Date`. EastWest yearless dates use the statement year or the immediately preceding December/year as appropriate; impossible dates remain ineligible rather than searching historical leap years.
- Malformed/unrecognized activity produces a partial warning when usable rows remain; unsupported/ambiguous identity or no parsed rows fails safely. Even a matched reconciliation leaves completeness uncertain. Engine/raw text is transient and absent from the handoff. Native adversarial/partial-format acceptance remains pending; fixture success is not a claim of broad provider-variant support.
