# IP-05 Task 01 integration notes

- Review initialization is explicit: capture the current scope with `statementImportStore.captureReview()`, then call `initializeReview(scope)`. It consumes only the store's current `ready.result`; repeated calls preserve the existing review snapshot. The Select view does not initialize review yet; the later review controller must call this entry point. `session.ts` needed no production changes because its existing import-store synchronization and unsaved-work policy already cover the new phases.
- `updateReview(scope, event)` currently owns tentative editor, filter and catalog request outcomes only. Task 2 must decode/validate the combined catalog before delivering `catalogSucceeded`; the foundation checks destination and request identity, not catalog completeness. After authentication generation changes, an old loading request remains retained but cannot deliver. The controller must issue a fresh request with the newly captured scope and a unique request ID, rather than treating retained `loading` as a live request.
- Applied row/Rule commands and revision increments belong to task 3. Extend the store's writable-action classification when adding those events; currently only `editorChanged` requires write access, while inspection/filtering and catalog reads work in archived Spaces. Add Continue's write guard in task 5. Tentative changes invalidate a handoff without incrementing the applied review revision.
- `review-ready` and `ReviewHandoff` are lifecycle/type scaffolding. There is intentionally no command to construct a handoff or enter that phase before task 5's full validation. A synthetic boundary fixture tests suspension/recovery and Back retention without implying that confirmation validation exists.
- No native APIs, dependencies or UI interactions were added. Native review acceptance is still pending the later controller/view tasks; the prior IP-04/#138 device and parser-certification gaps remain open.
