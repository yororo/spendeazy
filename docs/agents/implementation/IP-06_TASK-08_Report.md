## Persistence and execution seams

- `importedAt` remains the only confirmation clock and maps to the response's `confirmedAt`; there is no second timestamp. Historical imports keep null complete provenance and totals. Aggregate original totals use unrestricted numeric storage rather than one Expense's numeric(15,2) ceiling.
- Snapshot rows have unique import/source identity and a same-Space import FK. A generated Category ID from confirmed JSON has a same-Space Category FK. Expenses reference snapshot ID/import/Space/source together; the database rejects excluded snapshots, missing snapshots on complete imports, and provenance changes during later edits. Existing incomplete imports retain their legacy nullable path until Task 5 removes the old POST.
- The row and operation adapters take an existing transaction manager. Task 4 wires them through the new reviewed-import context with User → exclusive Space → operation lock order. The existing import Space guard now takes that exclusive lock after actor protection.
- `admit` returns an existing immutable hash rather than interpreting a conflict. The caller must compare hashes and terminal state. **Read successful operations with read authority before admission**: even a conflict-ignored INSERT executes the writable-Space trigger and would reject archived replay. End admission's short transaction before execution waits on actor/Space locks.
- Operation identity/hash/time and terminal state are database-immutable; one import can be referenced by only one successful operation. The operation port stores no financial request. Failure metadata retains a safe code and field/code pairs. Task 4 adds projected typed warning records/digest for immutable `IMPORT_REVIEW_REQUIRED` replay; do not persist the whole request or free-form exception messages. No elapsed-time lease or recovery executor has been introduced.
- Physical Personal cleanup order is Activity → Expenses → operations → imports (which cascade snapshots) → Categories/Space/User. Seed reset now removes operations before imports. Shared lifecycle behavior continues retaining financial history. This does not implement the broader account-deletion workflow.

## Tasks 3–4: historical execution details and recovery constraints

- `ReviewedImportService.preview` is the live stateless POST implementation. `confirm` is the tested application boundary returning `{result, replayed}`; there is deliberately no operation PUT route yet. Task 5 uses this service, removes the older POST and publishes the operation errors through the exception filter and generated OpenAPI. The following execution details still apply to recovery.
- The reviewed context is separate from the legacy confirmation context to keep the older POST/tests working until Task 5 removes them. Every participating adapter uses one supplied transaction manager. Admission ends before financial execution; both use actor/Space ordering, and admission rechecks an operation after taking the scope locks to handle a concurrent success/archive. Execution locks archived scopes without requiring writability, checks the operation, then applies write/Category guards only to pending execution. This distinction is required for successful replay.
- Duplicate-specific history reads batch fingerprints and scoped HMACs and deliberately include soft-deleted Expenses. Existing browsing/edit predicates remain unchanged. Reconciliation warnings inspect original assertions/diagnostics, missing comparison values, partial/failed extraction, and nonzero original differences, independently from edited spending. Warning identity now explicitly projects fields rather than spreading a runtime warning object, which could accidentally include its display message.
- Known application failures roll back the financial savepoint and commit only terminal safe metadata while the operation lock remains held. Refreshed warnings persist only IDs/types/scoped references, a digest, and fixed server messages; no review snapshot or raw duplicate reference is saved in the operation. Unexpected errors roll back the execution transaction and leave the separately admitted operation pending. Recovery must reuse this boundary and frozen request, without elapsed-time failure or another operation ID.
- Remembered Rules append under the existing Space lock, including conflict checks against inactive owners. Same-owner normalized duplicates are no-ops. Category revisions start at one; Space Rule revisions start at zero, so one newly affected batch produces Category revision two and Space Rule revision one. No review collection revision is checked and no matching reruns.
- Application admission validates the complete payload and protects references before calculating the request hash. Current Category checks intentionally occur only for pending execution, after terminal replay is checked. The older Task 1 pipeline note applies to new financial execution, not replay: revalidating current Categories before hash/replay would break immutable archived success.
