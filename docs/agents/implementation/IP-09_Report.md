# IP-09 consolidated handoff — Tasks 01–09

- Historical `deleted_at` rows migrate to User `deletion_status = 'completed'`, with null email/photo and the sanitized name. This describes the existing local tombstone only: their old Clerk IDs were already replaced, so no operation or provider/session completion evidence is fabricated. The legacy local-only deletion service/store path has now been removed.
- User `deleted_at` stays null while pending; the operation's `accepted_at` is the acceptance clock. Completion requires all three independent checkpoint timestamps, a completion timestamp, and cleared claim/retry/failure fields. A failed stage must not prevent successful independent checkpoints from being saved. Safe failure codes are an explicit SQL/TypeScript allowlist; the reconciler must translate provider/storage failures into these values rather than store raw errors.
- `UserRecord` is an active-only projection and keeps a non-null email. The entity permits null for scrubbed tombstones. Restricted operation lookup works independently of active User resolution and returns internal credential binding/progress; it must never become a normal profile response or grant route access.
- Migration rollback refuses to discard any operation or nullable-email tombstone. It does not reconstruct erased emails. Integration checks exercise both the safe rollback/reapply path and refusal with retained deletion state, inside a rolled-back transaction.
- Financial services previously passed authority checks separately from adapter reads/writes. The Users-owned active-execution port now wraps normal authenticated database requests and rechecks lifecycle inside its transaction. TypeORM adapters resolve an asynchronous transaction context only for their own DataSource; newly added adapters must participate too. Reads use repeatable read and shared locks. Financial writes keep read-committed isolation and shared actor locks so concurrent optimistic edits retain their existing behavior; invitation/leave mutations use exclusive participant locks. Actor and discovered membership/claim peers are locked in numeric order before Space work; membership changes cause a full rollback/rediscovery. New routes that change User rows or membership must select membership execution mode to avoid lock upgrades.
- Reviewed import preview/operation routes deliberately retain their independently committed unit-of-work boundaries. Their actor check/shared lock runs in every read/admission/execution transaction. Do not wrap these routes in the normal request transaction: doing so would roll back durable admission or terminal recovery metadata when the application subsequently throws. A status read paused behind an exclusive actor lock now waits for that lifecycle transaction; test barriers must release it before awaiting the response.
- Invitation participant fencing can make a join-winning rotation return the existing 409 ineligible error before rotation starts; a rotation-winning stale join remains 404. Invitation insertion uses wall-clock creation time because request transaction start precedes the application's seven-day expiry calculation.
- Acceptance owns archive notifications in the same transaction and removes every deleting-user membership, including old archives. Surviving members retain archive access; former contributors are returned separately in attribution, never restored as members. No immutable Shared evidence/results were rewritten.
- The worker uses five-second polling, a sequential five-operation batch, two-minute expiring claims, and bounded exponential retry with jitter. Provider Retry-After can exceed the fifteen-minute cap. Provider calls hold no database locks. The API must remain running; scale-to-zero deployments need a scheduled reconciler invocation before release. Normal shutdown hooks wait for an in-flight poll. Checkpoint writes and finalization match the current claim token; Personal purge is safe to replay after a lost checkpoint.
- Provider removal is followed by another session sweep before the revocation checkpoint. Missing session-list resources count as absence only after a separate provider-user 404; authentication/configuration failures and outages remain retryable failures. Successful revocation and lost responses are checked against terminal session state. Clerk session pagination/revocation signatures were checked against installed types and the official [listing](https://clerk.com/docs/reference/backend/sessions/get-session-list) and [revocation](https://clerk.com/docs/reference/backend/sessions/revoke-session) documentation.

## Mobile lifecycle nuances

- The SecureStore deletion marker is separate from import receipts and contains only provider User/session IDs and submitted/accepted phase. It is saved before DELETE. If acceptance persistence fails, the earlier submitted marker still gates restart conservatively. A 404 before acceptance, 401, sign-out or provider outage never proves completion. Explicit sign-out removes the identifying marker only after local cleanup and Clerk sign-out succeed. No deletion-specific credential/token copy is persisted. Storage-read failure blocks provisioning until recovery succeeds.
- Root navigation owns deletion recovery above SpacesProvider and all protected routes. Blocking a deleting identity invalidates the financial generation before response publication or cleanup. Account transport checks live Clerk credentials before/after token acquisition and on both request outcomes; it survives Space changes and financial-session clearing. New identities can enter a fresh financial session; another session of the deleting identity cannot borrow the initiating-session capability.
- Normal API deletion errors invoke the deletion owner and private cleanup. Generic 401 recovery reloads the live Clerk session: active status plus a refreshed token can restore same-owner drafts without replaying financial mutations. Confirmed session termination clears private work and fences only that ended credential, allowing a fresh same-user session. Deletion fences the entire old identity. A provider verification outage leaves the recovery gate and retained draft in place.
- Application cleanup runs outside route lifetimes. Receipt and remembered-Space writes serialize against removal; import invalidation clears extraction/password delivery and awaits late native copies before sweeping. Profile picker cleanup participates in the same retry gate. Appearance remains untouched. Completion proof remains recorded in the workflow even if device cleanup fails; the independent blocking cleanup surface owns retry. Offline devices are not remotely erased.
